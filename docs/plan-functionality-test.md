# 自動テストの計画書

更新日: 2026-09-20。状態: **承認済み範囲の実装・隔離環境での検証を完了**。公開サービスへの書き込み・マネージャ・実機の未検証範囲は[検証記録](../verification.md)を参照。

## 1. 目的と作業範囲

「コード上で動いていること」と「利用者が実際に操作して目的を達成できること」を区別し、後者を合格条件にする。起動、再生、設定、一覧、タグ、投稿を実際の配布物で検証し、未接続・不具合・退行を発見したら、期待値を緩めず製品実装を修正する。

計画拡充後、利用者から実装の承認を受けた。元の4フェーズに共通基盤の整備を加え、検出した不具合の修正と関連文書の更新まで行う。ニコニコ市場の削除もPhase 3で実施する。以下の合格条件を実行結果と照合し、計画の記載だけで完了と扱わない。

自動テストは可能な限りオフラインで完結させる。ただし、再生を模した時刻更新だけで実映像再生を合格にせず、固定データでの成功を現行サービスの認証・受理・保存成功と同一視しない。

本計画の承認だけでは、公開サーバーへのコメント投稿・タグ変更・マイリスト変更等は実行しない。実環境での書き込みは、対象アカウント・動画・変更内容・回数・後始末を具体化し、その操作への明示許可が得られた範囲で行う。一般的な実装着手の承認とは分ける。プッシュ・タグ・リリース公開も別の依頼に従う。

## 3. 検証の層と共通基準

### 3.1 検証の層

| 層                     | 目的                                             | 差し替えてよい境界                       | 成功しても保証しないこと             |
| ---------------------- | ------------------------------------------------ | ---------------------------------------- | ------------------------------------ |
| 単体                   | 時刻、並び順、入力検証、状態遷移、エラー処理     | 時計・乱数・通信・保存領域など           | 実画面からの操作、実映像、実サーバー |
| 結合                   | フォーム→処理→要求→応答→モデル・保存・表示の接続 | 最下流の通信・機器・保存失敗             | 現行サービスの受理、実機入力         |
| オフラインブラウザ     | 配布物を描画し、利用者の導線と入力で確認         | 通信境界で固定HTML・API・映像を応答      | マネージャ導入、現行DOM・API、認証   |
| 実サイト読み取り       | 現行DOM・API・再生資産との互換性                 | 原則差し替えなし。許可外の書き込みは遮断 | 実行していない投稿や変更             |
| 認証・マネージャ・実機 | 登録、権限、公開サービスへの反映、機器固有操作   | 検証目的の処理は差し替えない             | 未実施の環境・機器                   |

各ケースに層を明記する。内部モデルへのデータ投入は前提作成に限り、検証対象のクリック・保存・シーク・投稿処理を直接呼んで代替しない。内部状態は結果を補強する観測に使用できる。

### 3.2 全ケースの合格条件

- 入口→対象表示→実クリック・入力・選択→結果→閉じる／再表示まで確認する。非表示meta、DOMの存在、イベント発火、`isOpen`だけで合格にしない。
- 寸法・表示・クリッピング・重なり・ヒットテストを確認して入力する。Shadow DOM・隔離iframeにも対応し、覆われた要素へJavaScriptの`click()`を強制しない。
- 正常系だけでなく、空・上限・端点、不正入力、通信／保存失敗、キャンセル、再試行、動画切替・終了との競合を確認する。取消機能がない設定に一律の取消仕様を新設せず、実際の保存契約を固定する。
- 状態、描画、API要求、保存値のうち、その機能を裏付ける観測を組み合わせる。保存は実キー・型・期待値を比較し、再表示と文書再読み込みで確認する。`null`を変更前との差だけで成功にしない。
- 成功応答以外で成功表示を出さない。製品／Worker例外、未処理Promise拒否、CDPエラー、想定外通信を記録し、失敗にする。意図したエラーはケース単位で種類と件数を照合する。
- 待機には観測条件と上限を設ける。時刻・画像の許容差は測定条件とともに事前に決め、失敗後に緩めない。単体の時計は固定し、実再生は本物のmedia要素とフレームで測る。
- 選択には安定した`data-*`・設定キー・構造を使い、翻訳文言、生成クラス、固定画面座標に依存しない。識別子の追加は最小限とし、製品へテスト専用の成功分岐を入れない。
- 終了時はテスト所有のタブ・コンテキスト・PIDだけを片付ける。変更した値や関数をfinallyで復元し、cleanup失敗も元の失敗と併記する。

### 3.3 ケース台帳

実装開始時に本書のIDを親として、全ボタン・設定キー・メニュー項目・動的行操作を子ケースへ分解する。各行に「入口／前提／操作／期待結果／観測方法／異常系／保存・復旧／検証層／対応テスト／結果・証跡」を記録する。

状態は`未着手`・`実装済み未実行`・`合格`・`失敗`・`阻害あり`・`適用外（根拠必須）`を区別する。各ケースの実装先と確認範囲は[機能検証台帳](functionality-test-matrix.md)、実行結果はverification.mdと各レポートを参照する。条件付き表示、子画面、iframe内、スクロール後の項目も対象とし、画像取得だけを操作済みに数えない。

全要素の正常操作と適用可能な状態遷移を確認し、組み合わせは危険度から選ぶ。全設定値の総当たりは要求しないが、項目自体の未検証を組み合わせ削減の名目で省略しない。操作要素・設定が増えた場合は台帳への未登録を検出できるようにする。

## 4. Phase 0：オフライン基盤と実行環境

### 4.1 フィクスチャ・通信・映像

1. 採取済みHTML・APIを起点に、視聴、検索、タグ検索、関連動画、投稿者一覧、コメント、プレイリスト、認証状態を用意する。採取元・採取日・加工箇所・制約を記録し、人工データを実サーバー応答と偽らない。
2. 単一のsm9へ依存せず、長さ・比率・コメント分布・投稿者情報の異なる複数動画、空／欠落／非公開／失敗応答を用意する。DOMは実採取を基礎にし、独立した複数の構造でも入口を確認する。
3. 映像は権利上問題のない小さな生成素材を用意し、フレーム・経過時刻・画質を識別できるようにする。少なくとも2画質のHLS、初期化データ、セグメントで本物のデコード・シーク・終端を検証する。追加機能用WebMだけをHLSの代用にしない。
4. CDPのFetch等で応答し、未登録通信は外へ通さず失敗させる。iframe・Worker・新規タブ・Service Workerも点検し、故意の未登録要求で遮断漏れを検出する。前回キャッシュやService Workerによって偶然成功しない隔離環境にする。
5. メソッド、ホスト、パス、意味のあるクエリ、JSON／フォーム本文を照合する。キャッシュバスター等だけを明示的に正規化し、動画ID・ページ番号・時刻・タグ・本文を無視しない。条件や本文の異なる要求が同じ成功応答に一致したら失敗するテストを追加する。
6. 書き込みのフェイクAPIはシーン内だけに状態を持つ。成功した変更を次の取得へ反映し、失敗した要求では変更しない。要求履歴と再取得結果を照合し、常に成功JSONを返すだけのモックにしない。
7. 認証拒否、対象なし、競合、レート制限、5xx、不正JSON、切断、遅延、応答順序の逆転を各ケースへ割り当てる。公開API契約は既存実装・一次情報・実測から確認し、架空のURLや応答仕様を製品へ埋め込まない。
8. Cookie、トークン、署名URL、個人情報を採取後に除去する。必要なIDは整合するダミー値へ置換し、フィクスチャ・レポート・画像のGit差分を点検する。

既存`scene.ts`の緩い照合をそのまま投稿検証へ流用しない。既存用途を確認して必要な型・照合条件を拡張し、バイナリ応答を文字列へ再変換しない。新規依存は既存Bun・CDP・エンコード手段で不足する場合に限り、採用理由と再生成手順を残す。各フェーズ固有のデータはその実装時に追加する。

### 4.2 ランナーとCI

- `bun run dev`は現行の手動環境準備・登録までという契約を維持し、9333や実利用Firefoxを自動テストへ使わない。
- 既存ランナーと専用stateを再利用し、同時実行拒否・継承ポート無視・finally停止を回帰確認する。ケースごとに保存領域とフェイクAPI状態を初期化し、順序依存を除く。
- `bun run test:browser all --offline`を実装し、モード省略時もオフラインとした。実サイトは`--live`を明示する。投稿・タグ・マイリスト変更を行うスイートはオフライン専用とし、実サーバーへの認証書き込みは通常の`all`やCIに含めない。
- 既存Ubuntu品質ジョブを維持し、Windows用起動補助と整合するオフラインブラウザジョブを追加した。Chrome・依存の準備に必要な通信と、ケース実行中の外部通信ゼロを区別する。リモートCIはプッシュしていないため未実行。
- ビルドした実配布物を検証する。buildはdistを空にするため、distを読む単体テストと並列実行しない。同じcheckoutで複数ビルドもしない。
- CIは失敗時もケースID、理由、画像、必要な通信概要を保存する。0件実行、想定外通信、cleanup失敗、必須ケースの未実行を成功終了にしない。リリースの品質条件にもブラウザジョブを接続する。

**出口条件:** 外部へ接続せず、配布物の入口から生成HLSを再生・停止・シークできる。未登録要求で確実に失敗し、失敗時もテスト所有ブラウザを停止できる。

### 6.2 設定を全項目確認する手順

1. 9カテゴリの入力・ボタン、条件付き項目、型、最小／最大／刻み、全選択肢、既定値、保存方式、設定の利用先を台帳化する。一般設定は`data-setting-name`、追加設定は実定義とDOMを照合する。

### 実サーバーでの確認手順

1. 専用ログイン済みプロファイルと変更を許可された対象を用意し、秘密情報をログへ出さない。
2. 動画・投稿文／タグ変更／追加先・回数・復旧方法を具体化して許可を得る。取り消し可能と仮定せず、実仕様を確認する。
3. 許可された操作を1回行い、要求・受理結果・再取得した状態を記録。投稿前の情報取得要求と書き込み要求を区別する。
4. 反映待ちは上限を決める。未反映なら記録し、成功を得るために公開投稿を繰り返さない。後始末も許可範囲に限る。

許可・アカウント・権限が不足しても、オフラインの全経路検証と実行可能な修正は完了させる。実サーバー項目は阻害要因・代替確認・リスク・再開条件を記録し、P4全体を確認済みにしない。

**出口条件:** オフラインで認証別表示から1回の投稿・再取得・描画まで確認でき、許可済み実環境では実サーバー反映も確認できる。両者を別々に報告する。

## 10. 実装順序・成果物・完了判定

### 10.1 承認後の順序

1. **棚卸し:** Git状態と既存検証を確認し、ケース台帳と期待動作を固定。既存の失敗も原因を調査する。
2. **Phase 0:** 遮断・要求照合・生成HLS・隔離・後始末を整備し、最初の再生ケースをCIへ接続。
3. **Phase 1:** 起動→再生→操作→終端→closeを確立し、単体・結合・配布物操作で回帰確認。
4. **Phase 2:** 全設定と左メニューについて、画面・保存・機能反映を確認。
5. **Phase 3:** 一覧・行操作・メニューを検証。市場削除は周辺の回帰ケースを確立してから実施。
6. **Phase 4:** タグ・認証・投稿を通信境界まで接続。実書き込み内容を具体化し、許可範囲だけ実サーバー検証。
7. **最終確認:** 横断・環境差・導入経路を確認し、文書と配布物をそろえる。

各段階で「再現テスト→原因修正→同じテスト成功→関連回帰」の順に進める。既知不具合を最終段階まで放置せず、新規テストは通常ランナーへ接続する。1ファイル1000行以下を守り、既存巨大ファイルの分離前には変更前の動作を回帰テストで固定する。

### 10.2 成果物と記録

- ケース台帳、既存スイートに接続された単体・結合・ブラウザテスト。
- 採取根拠・加工内容を持つフィクスチャ、生成映像の再生成手順、遮断・照合の回帰テスト。
- 検出不具合の修正、市場機能撤去、必要な配布物更新。

### 10.3 最終検証

現行の品質コマンドは次の順で実行する。ブラウザの新モードは実装後にpackage.json・更新手順とそろえて追記する。

```powershell
bun run lint
bun run format
bun run type-check
bun run build
bun run test
bun audit
```

製品変更後は実配布物のブラウザ検証を行い、Worker・保存HTMLを含む既存回帰を維持する。修正後は対象と周辺を再検証し、理由なく成功済みの検証を繰り返さない。遮断・要求照合・重複防止等は、意図的な誤要求や重複入力を検出できることも確認する。

### 10.4 完了条件

- 全操作要素・設定・メニューにケースがあり、適用可能な正常系・異常系・境界・競合が実行されている。
- 利用者の入口から結果まで接続し、期待値を弱めず発見した製品不具合を修正している。
- オフライン実行中の想定外外部通信0件、想定外製品例外0件。cleanupとケース件数も整合している。
- 固定条件で再現可能で、ケース順・前回キャッシュ・保存値に依存しない。0件実行やスキップを合格に含めない。
- 型・lint・整形・ビルド・単体・結合・ブラウザ・CIの適用対象が成功し、distが生成元と一致する。
- 実測と代替検証を区別し、阻害項目の理由・証拠・再開条件を記録する。未実施の実投稿・実機・他ブラウザまで全機能確認済みとしない。
- 文書に変更範囲と結果が反映され、利用者の環境・設定・公開データに許可外の変更がない。
